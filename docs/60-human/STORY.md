# Sandwich 项目故事

本文是 Sandwich 的演进叙事，不是实现规范。

* 不作为工程规则依据
* 不作为 AI 默认输入文档
* 不作为架构设计说明

只记录“这支团队（含 AI）如何判断、取舍、修正”。

文中所有判断，均基于 commit 行为的观察性推断，而非作者主观表达。

---

## 第一阶段：旧项目先被接管，而不是被重写

【触发点】

最早的提交从 `Initial commit` 和 `init` 开始，但很快转向 `Add docs governance entrypoints`、`Docs(governance): 搬运文档串联与提交策略`、`Chore(api): 切换入口模块为jar打包`、`Refactor(api): 清理服务端页面依赖`。4 月 24 日当天出现高密度提交，`Docs`、`Refactor`、`Chore` 交替出现，说明项目不是从理想空白处搭起，而是先把一个旧项目放进可接管的轨道。

固定背景里，Sandwich 是 Bacon 的落地演示项目。从提交行为看，最早被搬进来的不是业务功能，而是文档治理入口、TODO 拆分、提交收口和持久化边界。人类更像持续给出方向、判断和约束；文档、代码、回退、测试和提交都由 AI 执行。

【关键动作】

第一组动作集中在入口和边界：API 应用从旧页面口径切到 jar 运行形态，`docs` 和 `TODO` 成为协作入口，`sandwish-infra` 子工程被建立，字典、日志、菜单、机构、角色、上传文件、用户、存储、辅助、会员等持久化链路被连续迁移。

第二组动作开始处理旧项目里的运行态含混：Redis 持久化被明确归入 infra，认证 Redis 状态被迁移为 DO 和装配器，用户、角色、菜单等持久化表达被重新收敛。提交颗粒度很小，常常是一个领域、一条链路、一次 TODO 调整。

【冲突 / 反复（关键加分项）】

这一阶段已经出现明显反复。`Docs(todo): 收窄认证 Redis 迁移子任务表述` 很快被 `Revert "Docs(todo): 收窄认证 Redis 迁移子任务表述"` 撤回，随后才是 `Feat(auth): 迁移认证 Redis 持久化到 infra` 和 `Feat(auth): 为 Redis 实体补充 DO 和装配器`。

这个波动说明认证 Redis 的归属并不天然稳定。它到底是缓存、运行态，还是持久化边界的一部分，需要先在 TODO 中试探，再通过回退和重做落到代码结构里。AI 高频提交和快速撤回，让这个判断可以被低成本试跑。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎不是先追求完整新架构，而是先验证一个更务实的判断：旧项目要被 AI 持续控制，第一步不是重写功能，而是让混乱有地方登记、有边界可拆、有提交可收口。Bacon 的方法论在这里更像被搬进现场的一套施工规程，先保证 AI 每一步都能解释自己在改什么。

## 第二阶段：模型隔离让旧系统开始说分层语言

【触发点】

4 月 27 日出现第一次密度突变，当天提交超过百条。提交主题从“搬持久化”转向“模型怎么分层”。`Docs(governance): 固化接口模型分层规则` 之后，用户、角色、机构、菜单、日志、字典、个人中心、后台认证、签名、密钥、异步任务、存储入口、前台登录状态等接口模型被连续隔离。旧项目里接口模型、领域实体和持久化对象混用的问题，在这一段被集中暴露。

【关键动作】

这一阶段先隔离 API 请求响应模型，再继续收敛机构、日志、字典、上传文件、存储、辅助、会员等 DO 和 assembler。与此同时，`Refactor(common): 收窄通用Crud契约`、`Refactor(sys): 收窄菜单树持久化契约`、`Refactor(common): 收敛实体查询契约`、`Refactor(api): 改用显式查询对象` 说明旧的万能 CRUD、树服务和泛化查询基类开始被怀疑。

门禁也在这一段出现。Request、Response、DO 注解规约先被写入文档，再通过 `Test(api)`、`Test(infra)` 固定成架构检测。文档不再只是说明，而是开始变成可以运行的约束。

【冲突 / 反复（关键加分项）】

这一阶段的波动点是 common 和 cache 的边界。提交先有 `Docs(cache): 增加common-cache判断手册`、`Docs(cache): 盘点缓存迁移现状`、`Docs(cache): 固定infra缓存契约`，又出现 `Docs(cache): 确认暂不建立common-cache`。但同一天后段又制定 common-cache 迁移计划，建立 common-cache 基线，接入 JetCache，并迁移系统、存储、认证、辅助状态。

这不是简单的摇摆，而是抽象条件变化后的重判。早期缓存更像 infra 内部细节；当多个模块都暴露运行态缓存、会话状态和限流状态之后，common-cache 才被允许成为公共能力。

【思路历程推测（观察语气）】

从这些提交看，更像是在把旧项目翻译成 Bacon 能控制的语言：HTTP 入口有请求响应模型，持久化有 DO 和 assembler，业务查询有显式 query，公共模块不再默认承载业务便利。AI 在一天内完成上百个小步提交，这种节奏更像一种可持续试错机制；人类只需要在边界判断上持续校准方向。

## 第三阶段：技术底座替换暴露出更多旧口径

【触发点】

4 月 28 日，提交主题集中到 MyBatis Plus。`Docs(persistence): 制定 MyBatis Plus 迁移手册` 之后，签名、会员、存储、日志、菜单、机构、角色、上传文件、用户加密、用户、字典等持久化连续迁移。这是一次技术底座替换，但提交模式显示它不是单纯换框架，而是在借新底座清理旧口径。

【关键动作】

这一阶段先修 Mapper 扫描和 DAO 分页契约，保证新底座可以运行；随后删除旧分页和 CRUD 支撑，统一分页参数与 upsert 命名。紧接着 `Build(quality): 搬运 Bacon 格式化配置` 出现，common、biz、infra、admin、front 被逐个格式化。

之后又出现 DO 手写访问器、无效 DO 主键构造器、DO 查询冗余字段、DAO 写入语义、持久化主键生成等清理。4 月 29 日继续用共享主键 DO 命名、数据对象主键规则、跨模块引用禁止、构造入口限制等测试门禁固化这些规则。

【冲突 / 反复（关键加分项）】

这一阶段的反复不是大规模 revert，而是“迁移后继续拆脚手架”。MyBatis Plus 迁移完成后，项目没有停在能运行，而是马上清理旧分页、旧 CRUD、手写访问器、无效构造器和冗余字段。

格式化配置也有类似意义。它表面上只是 style，但在 commit 序列里，它和 `validate执行spotless格式化`、成员声明顺序门禁、注解门禁一起出现，说明关注点正在从“代码内容正确”转向“代码形态也必须可治理”。对 AI 来说，形态稳定本身就是可持续控制的一部分。

【思路历程推测（观察语气）】

从这些提交看，作者似乎在验证另一个判断：旧项目不能只迁移功能，还必须迁移生成规则。AI 生成的代码如果没有统一格式、统一 DO 规则、统一主键策略，很快会再次滑回混乱。Bacon 的搬运因此逐渐从“规则文档搬运”变成“构建流程、测试门禁和代码形态一起搬运”。

## 第四阶段：领域语义从工具层里拿回来

【触发点】

4 月 29 日到 5 月 2 日，提交从持久化转向领域模型、接口层和查询层。`Refactor(common): 引入实体主键值对象`、`Docs(governance): 增加领域实体重塑手册`、`Test(architecture): 固定领域实体回流门禁` 后，系统、辅助、存储、会员实体被连续迁移。随后接口装配器、控制器基类、无效 VO、无效查询参数、分页响应命名等又被持续删除。

【关键动作】

这一阶段先增加实体主键值对象、领域能力接口和架构门禁，再迁移用户角色、基础实体、树形实体、辅助实体、存储实体、会员认证实体。之后删除旧实体继承链、归拢领域能力接口、删除无意义 ID 构造器、统一领域实体 ID 访问、删除领域身份基类，并最终合并领域基类到实体。

领域枚举也成组出现：异步任务状态、存储归属类型、日志类型、用户角色标记、菜单显示标记、会员启用标记、存储标记被改为业务枚举或业务状态。服务查询对象随后按字典、菜单、角色、用户、机构、日志、存储、会员、签名等领域迁移，并用门禁禁止 setter。

【冲突 / 反复（关键加分项）】

领域基类是这个阶段最有张力的波动点。提交先增加领域能力接口，又迁移实体；随后删除旧实体继承链、删除领域身份基类、提升 Lombok 访问器、展开默认值初始化、最终合并领域基类到实体。项目一开始需要基类帮助 AI 组织迁移，但当迁移推进后，基类本身又变成间接性来源。

接口装配器也有类似反复。先隔离接口模型，再静态化接口装配器，最后删除 ID 转换壳、未使用 API 模型和控制器基类。为了摆脱旧项目混用模型，先产生一批新结构；当这些结构被运行和门禁验证后，又被继续收窄。Sandwich 的治理不是追求更多层，而是追求可解释边界。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎从“让实体符合领域化形式”转向“让实体直接表达业务语义”。一开始可能需要接口、基类和值对象来摆脱旧结构；后面则更看重具体实体、具体枚举、具体方法名和具体查询对象。AI 在这里承担的是反复试错的执行，人类提供的是“这层是否真的有意义”的判断。

## 第五阶段：业务纵深开始验证治理是否真的能落地

【触发点】

5 月 3 日到 5 月 5 日，提交密度再次升高，主题从通用治理转向 storage、auth、OAuth、common 框架骨架、部署和真实运行边界。存储需求、数据库设计、私有资源校验、分片上传、认证身份凭据、认证会话、OAuth 令牌、对象存储抽象和 PR 质量门禁连续出现。

【关键动作】

存储侧先补私有资源访问校验、业务绑定查询过滤、资源逻辑删除、业务绑定约束，再引入本地存储后端抽象、分片上传持久化模型和分片上传业务编排。随后又制定对象存储迁移手册，收敛存储对象实体语义、服务引用端口、持久化端口、内容访问入口，并固定内容资源路径。

认证侧先固化后台认证模型需求和数据库设计，再增加后台登录标识、认证凭据、认证会话业务对象和持久化，切换后台登录身份凭据认证，写入会话生命周期。之后又处理会话运行态 Redis、OAuth 客户端、授权、刷新令牌、访问令牌、授权码流程、令牌撤销状态，并补充认证流程测试。

common 侧重新扩张：统一 API 响应、统一异常、请求上下文、当前用户契约、统一 ID、MyBatis 类型处理器、响应包装 Advice、声明式权限、操作日志、消息门面、对象存储抽象、S3 实现、数据库基线、Docker 部署样例、真实环境冒烟脚本和 PR 质量门禁都在这一段出现。

【冲突 / 反复（关键加分项）】

认证状态的归属是这一阶段的关键波动点。早期已经处理过 Redis 持久化归属，到这里又重新出现会话运行态 Redis 迁移。但这次不是重复，而是更细地拆分事实和运行态：认证会话作为业务对象持久化，Redis 作为运行态优先生命周期存储。

`Refactor(auth): 移除认证租户口径` 是另一个收缩信号。系统没有为了完整性保留多租户语义，而是在当前项目不成立时撤掉它。common 的扩张也不是回到早期泛化便利层，而是在多个领域证明统一响应、上下文、权限、ID、消息、对象存储这些能力稳定之后，才重新成为 Sandwich 自己的地基。

【思路历程推测（观察语气）】

从这些提交看，作者似乎在用 storage 和 auth 检验前面搬来的方法论是否有效。需求、数据库、领域对象、持久化、运行态、测试、清场可以围绕真实业务反复闭环，这说明 Bacon 的规则不只是文档管理技巧，而开始变成旧项目演进的执行系统。到这一阶段，所谓搬运已经不再像复制文件，而更像把外部工程判断放进 Sandwich 的问题现场接受验证。

## 第六阶段：从后端治理扩展到真实产品入口

【触发点】

5 月 6 日，提交从后端治理走向 admin-web、响应包装、当前用户和权限菜单。`Feat(admin): 初始化后台前端工程` 之后，后台前端组件库、路由菜单、前端代码规约、登录页面、登出入口、权限菜单接入陆续出现。与此同时，后端仍在收紧响应包装、Swagger、当前用户、公开方法、服务重载、用户账号拆分和接口权限注解。

【关键动作】

这一阶段把系统从“后端规则可控”推进到“产品入口也可控”。前端工程初始化后，很快接入组件库、路由菜单、状态查询测试、登录页、权限菜单、前端协作规约、命名目录规则、全局类型归属、根路径别名和前端边界门禁。

后端方面，响应包装从过滤器迁移到更清晰的统一包装路径，验证码图片适配、Swagger 分组排序、当前用户接口契约、菜单查询入口、当前用户业务编排、会员状态码、存储状态枚举、系统状态枚举、服务接口方法重载禁止等提交连续出现。用户账号身份服务、认证凭据服务、写入编排和当前用户菜单过滤也被拆开并测试固定。

【冲突 / 反复（关键加分项）】

这里的波动点是前后端治理的衔接。admin-web 不是单纯新增页面，而是先接入基础工程和规约，再接登录态、权限菜单、页面目录、服务归位和边界门禁。前端一进入项目，就被放进已经形成的治理框架里。

响应包装也经历多轮修正：先通过公共 Advice 建立统一响应，后面又有响应包装迁移手册、辅助签名响应包装、认证响应包装、移除响应包装过滤器、统一包装分页响应。这说明旧项目里响应口径并不统一，AI 需要多轮迁移、补丁和测试，才能让运行行为与治理规则一致。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎从“后端能被 AI 控制”扩展到“整个可运行产品都要被 AI 控制”。部署、冒烟、PR 门禁、前端目录、登录权限、响应包装都被纳入同一套节奏。人类没有直接编辑文件，而是在不断指定新的治理边界；AI 则把这些边界落实成工程、测试和提交。

## 第七阶段：全局 ID、认证主体和会话语义被重新统一

【触发点】

5 月 7 日到 5 月 8 日，提交密度保持高位。5 月 7 日先出现审计需求和审计数据库基线，随后是一整组雪花 ID 迁移：治理规则、系统/认证/存储/会员/审计数据库设计、schema、初始化数据、部署说明、领域标识、主键生成器、MyBatis 类型处理、各 domain ID 类型、API 边界 ID 类型、最终收口。5 月 8 日焦点转向 auth：Principal、PreAuthSession、主体认证会话连续出现。

【关键动作】

雪花 ID 迁移被拆成文档、SQL、数据、代码、domain、infra、API 边界和最终收口。每一步都有明确提交边界：先固定规则，再改数据库设计，再改 schema 和初始化数据，再改 common ID 能力，再按 domain 迁移业务和持久化 ID，最后迁移 API 边界并收口 RUNBOOK。

认证侧先补齐前台会员认证：会员主体模型、会员标识和凭据模型、登录表单运行态、注册接口、会员认证会话和 token、前台 token 认证。随后开始 Principal 改造：定义认证主体基础对象，增加统一认证主体结构，拆分统一认证主体服务，把认证读写迁到 Principal，并删除后台旧身份凭据模型、会员旧身份凭据模型、旧 SQL 和旧测试。PreAuthSession 再把后台和会员登录前状态下沉到独立服务，主体认证会话继续合并令牌、权限会话、OAuth 授权、登录事件和旧认证会话链路。

【冲突 / 反复（关键加分项）】

雪花 ID 的迁移体现了很强的“搬运后再项目化”特征。它不是在某个文件里把 String 改成 Long，而是先讨论 ID 规则、审计 objectId 是否仍为 String、idempotencyKey 与 id 的区别、expectedVersion 如何产生，再拆成 RUNBOOK 和 TODO，最后按文档、SQL、代码、API 边界逐段提交。

认证系统的反复更明显。前台会员认证刚被补成完整链路，随后又被 Principal 改造吸收；PreAuthSession 刚被下沉，后面又有主体认证会话把 token、权限会话和 OAuth 令牌统一起来。如果只看单个提交，会像是反复重做；从连续行为看，更像是先让每条链路具备完整事实，再发现重复语义，再把重复语义抽成主体中心，最后删除旧链路。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎已经从“把旧项目治理起来”转向“让治理本身可复制”。雪花 ID 和认证主体都展示了一种成熟路径：先从 Bacon 的工程控制方式中搬来规则表达和任务拆分，再针对 Sandwich 的现实拆出 RUNBOOK，再让 AI 小步迁移、测试、删除旧模型、清理现场。到后期，Bacon 的规则不再只是被引用，而是变成 Sandwich 自己的提交、门禁和文档节奏。

## 第八阶段：持续治理开始处理更细的边界污染

【触发点】

5 月 9 日到 5 月 11 日，提交仍然高密度运行。主题先从服务方法规约化切入，再进入审计、响应模型装配、Controller 映射、ID 转换适配、Sortable 排序、异常分层、统一主体上下文、通用工具清理和头像统一存储。这些主题看似分散，但 commit 模式都指向同一件事：旧项目中还能工作的边界污染，被继续识别、拆除、重建和门禁化。

【冲突 / 反复（关键加分项）】

审计的关键波动是“先拆字段，再建审计”。旧项目里审计字段曾经散在业务表和响应模型中，看起来能提供追踪信息，但也把横切能力塞进了每个业务对象。5 月 9 日的提交没有直接叠加新审计，而是先移除业务表审计字段、删除自动填充拦截器、退出旧规则，再建立独立审计领域和注解运行时。这一段不稳定，因为它必须承认旧做法可运行，却不再适合持续演进。

排序的反复更集中。5 月 10 日先有 Sortable 文档合并和单域 RUNBOOK，随后又出现 `Docs(sortable): 重建SORTABLE改造RUNBOOK并重写TODO任务`。5 月 11 日里，`Feat(member): 完善 Member 排序能力与 priority 全局约束` 之后又有 `Fix(member): 去除 Member 排序链路 scope 分离`，接着 `Feat(sys): 统一 User/Role 排序为全局 priority`。这说明排序语义一开始在“按 scope 排序”和“全局 priority”之间摇摆，直到通过 Member、User、Role 的实际改造才收敛。

异常分层和上下文门面则像是后期治理的另一种反复：早期 common 已经有统一异常、请求上下文和当前用户契约，5 月 11 日却继续删除无效异常、迁移文案解析、增加转换层、统一主体上下文。这说明先前的公共能力虽然让系统跑起来，但还没有完全消除入口层、业务层、common 层之间的语义混杂。后期提交更像是在把已经成形的地基再次打磨到可长期演进。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎已经进入持续演进阶段：不再只是把旧项目变得能跑、可用、可恢复，而是在每次新增能力时先问它会不会污染边界、会不会留下不可治理的输入口、能不能被门禁和提交收口固定。审计把横切历史从业务表里拿出来，排序把 UI 输入、业务规则、持久化约束和错误码一起收束，异常分层把“能抛错”推进到“入口可转换、业务可表达、文案可治理”，主体上下文则把前后台身份解析从散落状态收回同一个门面。

## 第九阶段：真实入口把治理推到用户、第三方、服务器和前端规则面前

【触发点】

5 月 12 日到 5 月 20 日，提交没有真正降速。类型发生明显变化：`Style(admin-web)`、`Feat(admin-web)`、`Fix(admin-web)` 密集出现，随后进入 `Feat(open-api)`、`Docs(open-api)`、`Test(smoke)`、`Test(load)`、`Feat(deploy)`、`Test(cache)`，再继续推进到 `Docs(integration-test)`、`Test(integration-test)`、`Test(ci)`、审计页面收口，以及 5 月 19 日到 5 月 20 日成组出现的 `Docs(admin-web)`、`Fix(admin-web)`、`Chore(admin-web)` 前端治理提交。这个阶段显示项目开始从“可治理的后端系统”进入“真实管理台、第三方接口、服务器部署、负载模式、集成环境、审计入口和前端生成规则都必须可治理”的状态。

【关键动作】

第一组动作集中在用户管理页和管理台工作流。用户表格固定操作列、列宽拖拽、高级过滤、批量操作、拖拽排序、移动端布局、悬浮滚动条、操作列间距和排序手柄被连续打磨。随后又抽取通用页面外壳、筛选面板、批量操作条、玻璃表格、列表页组合组件和确认弹窗，并增加页面样式门禁。前端不是一次写完页面，而是先暴露重复，再抽出组件，再用规则限制组件放置。

第二组动作把管理台扩展到部门、菜单、系统日志、角色权限、存储对象和提交内容：部门树初始化数据、部门维护、部门层级调整、菜单树维护、日志列表、角色权限管理、用户部门侧栏、用户服务端数据、后台用户初始化数据、存储对象列表、提交内容后台接口和提交内容管理页都在这一段出现。对应后端也持续修正用户分页响应、角色名称返回、登录名可用性、用户编辑权限、用户角色保存、无用户系统日志、提交排序规则和存储归属类型。

【冲突 / 反复（关键加分项）】

这一阶段最明显的波动，是“界面可用”和“规则可控”之间的来回。5 月 12 日用户页先经历大量视觉和交互微调，紧接着 5 月 13 日就出现前端通用组件命名边界、组件放置规则和页面样式门禁。提交序列像是在承认一个现实：真实页面会迅速制造重复和局部技巧，如果不及时把这些技巧收回组件和门禁，前端会成为新的失控面。

另一个波动点是 Swagger 的快速回退：`Fix(swagger): 关闭后台文档 csrf 探测异常` 随后被 `Revert "Fix(swagger): 关闭后台文档 csrf 探测异常"` 撤回。这组很小的提交不像功能失败，更像一次边界试探：遇到文档探测异常时，直接关闭探测不是稳定答案。AI 可以快速试错，但最终仍要服从更窄、更可解释的安全和入口规则。

资源预览链路也经历连续修正。先让头像地址包含上下文路径，再让预览地址包含上下文路径、携带访问令牌；接着又让资源地址不携带令牌，改由 admin-web 使用当前令牌，最后后台预览不按归属拦截。这个过程显示旧项目里“文件能打开”并不等于资源访问语义清楚。真实页面一接进来，存储、认证、前端和后端路径马上开始互相校正。

开放接口和压测链路也表现出后期治理的另一种反复。开放 API 先从需求和鉴权设计开始，接着建入口模块、业务模型、后台管理、签名认证、开放提交接口，再修复密钥重置、API KEY 复制和凭据展示。5 月 16 日的 smoke/load 提交也不是一次写完脚本，而是先重整冒烟脚本，再增加接口面点火，再沉淀压测手册、测试环境样例，最后固定 `sandwish/k6` 镜像。这里的反复不是功能摇摆，而是把“服务器上怎么验证”也纳入可复现系统：脚本、环境变量、报告模板和镜像 tar 都必须能解释。

5 月 17 日的 cache sync 又把这个判断往前推了一步。单实例 smoke 能证明入口能跑，但不能证明两个或三个 API 实例在负载均衡后共享同一份运行态事实。`Fix(cache): 支持多实例缓存和nonce防重放` 之后紧接 `Test(cache): 增加多实例缓存同步脚本`，再接 `Fix(cache): 兼容前台缓存同步响应` 和 `Test(cache): 补充缓存同步矩阵覆盖`，这组提交像是在把刚暴露出的盲区迅速围起来：缓存不只是实现细节，而是部署拓扑的一部分。最后的 `Fix(open): 修复nonce存储启动注入` 说明 Open API nonce 防重放在负载模式下还经历了一次启动注入层面的修正，判断并非一开始就稳定，而是在 A/B/C 脚本验证中被继续收紧。

5 月 18 日到 5 月 19 日的集成测试建设，是这一阶段新的波动点。它先不是直接写大量测试，而是从集成测试建设手册、环境变量样例、服务编排、健康检查和测试数据库脚本开始，把“怎么避免误连真实环境”“验证码如何白名单”“测试数据如何清理”这些运行风险先圈住。随后才出现后台、前台、开放接口的配置、防误连保护、客户端、清理支撑、基类和业务数据。最后再一组组补后台认证、用户角色、系统、开放客户端、存储、提交内容、审计、前台注册和开放接口测试，并接入 PR 门禁。这个节奏像是在承认：单元测试和 smoke 可以证明局部正确，但旧项目真的进入持续演进后，还需要一个可重复、可清理、不会误伤环境的集成测试场地。

5 月 19 日到 5 月 20 日的 admin-web 规则收紧，是本阶段最后一个明显波动点。它不是先写一份大而全的前端规范，而是先把真实页面做出来、用 Playwright 和页面观察发现表格操作列、筛选区、抽屉按钮、Switch、Tag、service 类型、选项接口等摩擦，再把稳定下来的判断沉淀成组件、ESLint 门禁和更短的规则文档。许多 `Docs(admin-web): 删除...` 与 `Fix(admin-web): ...门禁` 成对出现，像是在不断把“需要人记住的 review 规则”改造成“代码里已经站住的默认行为”。`console.log` 和显式 `any` 最终被收进代码质量门禁，也延续了同一个判断：AI 生成前端代码时，规则越能机器阻断，后续对话越可以集中在业务判断上。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎进一步移动了：治理不再只停留在架构边界、领域语义和测试门禁，而是被推到用户每天会点击的页面、第三方会调用的开放接口、服务器会执行的部署脚本、压测报告、负载均衡后的多实例运行态、PR 前必须经过的集成环境，以及 AI 每次生成前端代码时会触碰的 ESLint 规则里。管理台页面的反复细修通常意味着系统已经进入真实使用前的磨合；开放 API 的连续提交则像是在把“外部访问者”也纳入 Sandwich 的规则系统；而 smoke/load/k6/cache sync/integration-test 的出现，说明部署后验证不再依赖人工经验，而要被脚本、镜像、矩阵、测试数据、清理机制和报告格式固定下来。

这些反复出现的动作，逐渐形成一种稳定偏好：先把外部工程判断搬进来，再用 Sandwich 的旧项目问题验证它；如果验证中发现概念过大，就收窄；如果发现重复需求，就抽象；如果发现旧口径还能跑但不可控，就拆除并重建；如果真实页面、开放接口、Docker 部署、压测、多实例缓存同步、集成测试和 admin-web 规则暴露新问题，就继续把它们纳入同一套提交、门禁、脚本和文档节奏。所谓搬运，在这里更像是把一套外部工程判断放进旧项目里接受验证，而不是机械复制文件。到后期，Bacon 的规则不再只是被引用，而是变成 Sandwich 自己的提交、门禁、组件边界、开放接口边界、部署脚本、冒烟脚本、压测镜像、cache sync 矩阵、集成测试数据、前端 ESLint 规则和报告收口方式。项目也因此从“混乱”走到“能跑”，再走到“可用、可恢复、可约束、可治理、可持续演进”。
