# Sandwich 项目故事

本文是 Sandwich 的演进叙事，不是实现规范。

* 不作为工程规则依据
* 不作为 AI 默认输入文档
* 不作为架构设计说明

只记录“这支团队（含 AI）如何判断、取舍、修正”。

文中所有判断，均基于 commit 行为的观察性推断，而非作者主观表达。

---

## 第一阶段：从能跑到先把边界画出来

【触发点】

项目一开始并没有直接冲向功能扩张。`Initial commit` 和 `init` 之后，紧接着出现的是 `Add docs governance entrypoints`、`Docs(governance): 搬运文档串联与提交策略`、`Chore(api): 切换入口模块为jar打包`、`Refactor(api): 清理服务端页面依赖`。这一组提交显示，系统最早处理的是运行形态和治理入口，而不是把更多业务堆进来。

【关键动作】

可以看到几个动作很早就出现：入口模块从页面服务口径切向 jar API 口径，文档开始承担协作入口，`docs/todo` 被用来记录和拆分持久化抽取讨论。随后 `sandwish-infra` 子工程被建立，系统模块的字典、日志、菜单、机构、角色、上传文件、用户等持久化链路被连续迁移到 infra。

这些提交的颗粒度很小：一个领域、一条链路、一次收口。它不像一次性“大重构”，更像先把旧系统里纠缠在业务层的持久化动作逐个拆出来，让之后的判断有地方落脚。

【冲突 / 反复】

这一阶段已经出现了不稳定信号。`Docs(todo): 收窄认证 Redis 迁移子任务表述` 后面马上跟着 `Revert "Docs(todo): 收窄认证 Redis 迁移子任务表述"`，随后才是 `Feat(auth): 迁移认证 Redis 持久化到 infra` 和 `Feat(auth): 为 Redis 实体补充 DO 和装配器`。这不是一个平滑的执行序列，而是先试图收窄任务，再撤回，再通过代码和模型补齐重新推进。

这个波动点很重要：它说明 Redis 到底算运行态缓存、持久化实现，还是业务对象的一部分，当时还没有完全稳定。最终的提交更像是在承认，认证状态需要落到 infra 的持久化实现边界里，但表达方式需要通过 DO 和装配器来固定。

【隐含判断】

从这些提交看，项目早期更像是在建立“能迁移、能收口、能解释”的工程节奏。文档不是附属物，而是和代码迁移一起出现；每个迁移动作都尽量对应一个可提交的闭环。这种节奏在 AI 参与下尤其明显：小步提交让试错成本降低，也让回退本身变成可以被记录的工程动作。

## 第二阶段：模型隔离与持久化表达的连续拆分

【触发点】

4 月 27 日开始，提交密度明显升高，主题从“把持久化搬到 infra”转为“每层模型应该长什么样”。`Docs(governance): 固化接口模型分层规则` 后面，是一串 `Feat(sys): 隔离用户接口模型`、`隔离角色接口模型`、`隔离机构接口模型`、`隔离菜单接口模型`、`隔离日志接口模型`、`隔离字典接口模型`。这说明项目开始意识到，只有持久化边界还不够，HTTP 入口模型也要从业务实体中切开。

【关键动作】

这一阶段的动作非常连续：后台系统、认证、辅助、前台会员登录状态都在做接口模型隔离；随后又回到持久化表达，继续收敛机构、日志、字典、上传文件、存储、辅助、会员等 data object 和 assembler 表达。

同一天还出现了 `Refactor(common): 收窄通用Crud契约`、`Refactor(sys): 收窄菜单树持久化契约`、`Refactor(common): 收敛实体查询契约`、`Refactor(api): 改用显式查询对象`。这组提交通常意味着旧的通用 CRUD、树服务、查询基类开始被怀疑。项目不再满足于“公共工具能用”，而是开始要求公共契约必须能解释自己的边界。

【冲突 / 反复】

这里的关键波动点是“通用能力”的反复收缩。先有公共 CRUD、树、查询契约的收窄，再有 `Refactor(common): 拆分公共基础模块` 和 `Feat(common): 引入MyBatis-Plus基础配置`。可以看到，公共层不是被简单扩大，而是在删除、拆分、再补基础设施之间来回校准。

这种阶段不稳定来自一个常见问题：公共模块如果太早抽象，会吞掉业务语义；如果完全不抽象，又会让后续迁移重复。提交记录显示，项目更像是在把“可复用技术能力”和“业务默认行为”拆开，而不是追求一个万能 common。

【隐含判断】

从这些提交看，接口模型隔离和持久化表达收敛是互相推动的。入口层一旦不再直接拿实体说话，持久化层也更容易只承担数据装载和映射。这个变化通常意味着系统开始从“能完成请求”走向“请求、业务、数据各自说自己的语言”。

## 第三阶段：门禁开始接管口头约定

【触发点】

同在 4 月 27 日，commit 类型发生了明显变化：`Docs(api): 明确Request注解规约口径`、`Test(api): 增加Request注解规约门禁`、`Test(api): 迁移Request必需注解`，随后是 Response、DO 注解规约门禁。文档和测试第一次形成非常紧的循环。

【关键动作】

这一阶段的关键动作包括建立 `common-test` 规约模块，增加 Request / Response / DO 注解检测，把 API 模型和持久化对象的注解要求变成可运行的架构测试。之后缓存边界、安全迁移也采用了类似路径：先写迁移手册和判断手册，再盘点现状，再落代码，再清现场。

权限整改尤其明显：`Docs(security): 制定权限整改运行手册` 之后，出现 `Feat(security): 建立通用权限匹配模块`、`Feat(security): 增加权限会话服务`、`Feat(auth): 登录写入权限会话`、`Feat(auth): 接入Spring Security令牌认证`、`Test(auth): 补充权限会话认证测试`。这不是单点修补，而是从规则、模块、登录流程到测试的一整串闭环。

【冲突 / 反复】

缓存是这一阶段最大的波动点之一。提交先写 `Docs(cache): 增加common-cache判断手册`、`Docs(cache): 盘点缓存迁移现状`、`Docs(cache): 固定infra缓存契约`，然后出现 `Docs(cache): 确认暂不建立common-cache`。但不久之后，又有 `Docs(cache): 制定common-cache迁移计划`、`Feat(cache): 建立common-cache基线`、`Feat(cache): 接入应用JetCache配置`，以及系统、存储、认证、辅助状态到 JetCache 的连续迁移。

这个事件体现出判断没有一开始就稳定：缓存究竟是 infra 里的实现细节，还是 common 层需要提供的基础设施，先被否定，后又在更多迁移压力下被重新接受。收敛过程不是“想清楚再动手”，而是通过字典、存储、机构、菜单、角色、用户等迁移经验，逐步逼出 common-cache 的边界。

【隐含判断】

这一阶段可以看到“文档 → 门禁 → 修复 → 再提交”的循环开始稳定出现。它不像传统的一次性设计评审，更像是一种可持续试错机制，在 AI 参与下成本显著降低：规则可以快速落成测试，测试暴露的形态问题又能被快速拆成下一组小提交。

## 第四阶段：MyBatis Plus、格式化和数据对象规则的收紧

【触发点】

4 月 28 日，提交主题突然集中到 MyBatis Plus：`Docs(persistence): 制定 MyBatis Plus 迁移手册` 后，是签名、会员、存储、日志、菜单、机构、角色、上传、用户加密、用户、字典等持久化到 MyBatis Plus 的连续迁移。这是一次明显的技术底座替换。

【关键动作】

这一阶段先通过 Mapper 扫描修复和 DAO 分页契约调整保证新底座能跑，再把旧分页和 CRUD 支撑删除。随后出现格式化配置接入和一组 `Style(common/biz/infra/admin/front)`，说明项目不只在迁移运行逻辑，也在把代码形态统一起来。

之后的提交继续向细节推进：删除 DO 手写访问器、无效 DO 主键构造器、DO 查询冗余字段，明确 DAO 写入语义，使用持久化主键生成，并把 DO 主键生成规约写入治理文档。

【冲突 / 反复】

这一阶段的波动不表现为明显回滚，而表现为“迁移后继续拆掉迁移脚手架”。MyBatis Plus 切换完成后，并没有停在“能跑”，而是马上删除旧分页、旧 CRUD、手写访问器和无效构造器。可以看到，迁移初期为了速度保留了一些兼容结构，但后续提交很快把它们清理掉。

另一个细节是质量工具的角色开始变得清楚。格式化配置被搬运后，不是停留在配置，而是按模块逐个应用。后续又有 `Build(governance): validate执行spotless格式化`，这说明代码形态不再依赖人工记忆，而是进入构建生命周期。

【隐含判断】

从这些提交看，项目开始把“迁移成功”定义得更严格：不是新框架接上就结束，而是旧抽象、旧字段、旧构造入口也要拆掉。这个阶段更像是在把技术替换变成一次结构清理，避免新旧两套口径长期并存。

## 第五阶段：领域实体回流与语义命名的再整理

【触发点】

4 月 29 日到 4 月 30 日，提交从持久化对象转向领域实体。`Refactor(common): 引入实体主键值对象`、`Docs(governance): 增加领域实体重塑手册`、`Test(architecture): 固定领域实体回流门禁` 之后，一组系统、辅助、存储、会员实体被迁移。这里的关注点已经从“数据怎么存”转向“领域对象该承担什么语义”。

【关键动作】

这一阶段先收敛实体身份能力，增加领域能力接口，然后迁移用户角色、基础实体、树形实体、辅助实体、存储实体、会员认证实体。接着又删除旧实体继承链、归拢领域能力接口、删除无意义 ID 构造器、统一领域实体 ID 访问、删除领域身份基类，最后合并领域基类到实体。

领域枚举也在同一阶段成组出现：异步任务状态、存储归属类型、日志类型、用户角色标记、菜单显示标记、会员启用标记、存储标记被改为业务枚举或业务状态。紧接着，标记更新方法也被改为业务命名。

【冲突 / 反复】

这个阶段很不稳定，尤其是领域基类。提交先增加领域能力接口，又迁移实体；随后删除旧实体继承链、删除领域身份基类、提升 Lombok 访问器、展开默认值初始化、最终合并领域基类到实体。也就是说，项目并不是简单地从贫血实体跳到一套新的继承体系，而是在尝试后发现某些基类本身也会制造间接性，于是继续把能力压回具体实体。

这是一段很有张力的演进：一开始需要基类和接口帮助迁移，但当迁移完成后，这些中间结构又开始显得多余。提交记录显示，项目更愿意保留具体语义，而不是为“领域化”保留一层看起来漂亮的继承结构。

【隐含判断】

这一变化通常意味着系统开始重视命名本身的业务含义。`displayFlag`、`enableFlag`、`roleFlag` 这类旧式标记逐步被 `MenuVisibility`、`MemberStatus`、业务枚举替代。业务语义不再藏在 `"0"` / `"1"` 或工具方法里，而是进入类型、方法名和边界转换。

## 第六阶段：接口、查询和控制器从框架壳里撤出来

【触发点】

5 月 1 日到 5 月 2 日，提交又转向接口层：接口装配器去 Spring 依赖、展开基础映射、删除未使用 API 模型、静态化装配器、使用方法参数校验请求、规范 DAO / Service 接口命名。之后，控制器基类、模块路径状态、无效统计响应模型、查询参数模型被连续清理。

【关键动作】

这一阶段做了三类动作。第一类是装配器收窄：接口装配器不再承担 Spring Bean 状态，内部方法也被收窄，ID 转换壳被删除。第二类是查询对象迁移：字典、菜单、角色、用户、机构、日志、存储、会员、签名等服务查询对象被迁移到明确目录，并用架构测试固定位置与 setter 约束。第三类是控制器形态 REST 化：存储控制器改造为 REST 接口，分页响应命名去 VO 化，控制器命名去 Api 化，接口请求响应模型下沉。

【冲突 / 反复】

这里的波动点是“接口模型到底该放在哪里”。4 月 27 日先完成了一轮接口模型隔离，5 月 1 日又删除未使用模型、静态化装配器、下沉 HTTP 接口契约到控制器。说明第一次隔离解决了实体外泄，但也留下了一些新壳：VO、装配器 ID 转换、无引用查询参数、控制器基类。

后续提交没有把这些壳继续扩大，而是逐个拆掉。这个阶段更像是在给上一轮接口隔离做二次修剪：保留请求/响应模型的明确边界，删除为了隔离而产生的过度包装。

【隐含判断】

从这些提交看，项目对“框架感”的容忍度在降低。控制器不再继承通用基类来获得路径和工具方法，服务查询对象也不再靠 setter 随意拼装。接口层开始变得更直接：请求绑定、参数校验、响应转换都在入口附近完成，业务查询语义则交给 service query 对象。

## 第七阶段：存储与认证从补丁走向完整业务能力

【触发点】

5 月 3 日到 5 月 4 日，提交密度再次升高，但主题不再是通用重构，而是两个业务纵深：storage 和 auth。先有前台登录 REST 化、前台认证控制器合并、旧签名拦截和 UEditor 支撑删除；随后是存储需求、数据库设计、上线检查清单，以及一组存储安全和分片上传实现。

【关键动作】

存储侧先补私有资源访问校验、业务绑定查询过滤、资源逻辑删除、业务绑定约束，再引入本地存储后端抽象和分片上传持久化模型，最后实现分片上传业务编排。认证侧则从身份凭据迁移手册开始，逐步增加用户身份、认证凭据、认证会话业务对象和持久化，再切换后台登录身份凭据认证，写入会话生命周期，并补齐模型测试。

之后认证运行态又被拆开：会话 Redis 运行态先被下达任务和固定口径，再增加运行态端口、实现 Redis 存储、切换优先生命周期、补测试、清理 TODO 和失效 runbook。可以看到，同一个认证主题不是一次完成，而是业务对象、持久化、运行态、测试、文档清场多轮推进。

【冲突 / 反复】

这一阶段的波动点是认证状态的落地位置。早期已经处理过 Redis 持久化归属，到 5 月 4 日又重新出现会话运行态 Redis 迁移。这次表达更精细：认证会话作为业务对象落地，Redis 则作为运行态优先生命周期存储。它不是简单重复，而是把“持久化事实”和“运行时状态”拆成两种对象。

OAuth 也有一段连续收敛：先增加客户端、授权、刷新令牌、多登录方式、授权码流程；再制定 OAuthToken 正规化手册，增加访问令牌持久化端口，正规化授权流程，支持令牌撤销状态；最后移除认证租户口径并强化令牌安全语义。`Refactor(auth): 移除认证租户口径` 是一个很清晰的收缩信号：系统没有为了看起来更完整而保留多租户语义，而是把当前不成立的模型撤掉。

【隐含判断】

从这些提交看，项目开始把“业务能力完整”看作多个层面的合成：需求文档、数据库设计、领域对象、持久化端口、运行态存储、安全校验、测试和清场。这个阶段不像早期只是在搬结构，它更像是在用已经形成的工程节奏补齐真正的业务纵深。

## 第八阶段：common 地基补齐与旧全局口径清除

【触发点】

5 月 5 日，提交主题集中到 common 框架骨架和旧模型清理。前半段先处理系统域里的具体语义：用户身份凭据、用户认证字段、用户实体角色承载、部门薄方法、用户等级值对象、访问等级值对象、旧上传文件模型、旧验证码 Servlet。随后出现 `Feat(swagger): 增加通用Swagger配置模块` 和一组 common-web、common-core、common-security、common-mybatis 的基础设施提交。

【关键动作】

这一阶段补齐了统一 API 响应、统一异常、统一异常响应处理、请求上下文传递、当前用户契约、统一 ID 生成、EntityId 类型处理器、JSON 列表类型处理器。随后又补 ResponseBodyAdvice、声明式权限注解、Spring 当前用户解析、后台接口权限注解、common web/security/mybatis 自动配置和架构规则复用支持。

最后一组提交继续扩展 common：统一操作日志框架、统一消息发送门面、日志接入消息门面、并发和路径架构规则、API 注解架构规则、对象存储抽象、本地和 S3 实现、基于对象存储重建 storage 后端适配。紧接着，旧本地存储后端、全局静态配置、无效异常构造方法、失效占位文件都被清掉。

【冲突 / 反复】

这一阶段最值得注意的是 common 的再扩张和再清理同时发生。早前项目多次收窄 common，删除 CrudService、RedisClient、无效公共类；到 5 月 5 日又大规模补 common-web、common-security、common-mybatis、common-log、common-mq、common-oss。区别在于，这次 common 承载的是统一响应、上下文、当前用户、类型处理器、消息门面、对象存储这样的框架地基，而不是业务默认流程。

`Refactor(core): 清除全局静态配置` 也是一个收口信号。早期系统里的 `"1"` / `"0"`、显示、启用、真假等全局常量被拆掉，说明项目不再接受一个“哪里都能拿”的静态入口。到这里，公共能力可以存在，但必须有明确职责；业务编码则回到枚举、值对象、assembler 或具体边界里。

【隐含判断】

这些反复出现的动作，逐渐形成一种稳定偏好：先允许小步迁移用临时结构推进，再用文档、测试和清场提交把临时结构撤掉；先把不清楚的能力收窄到具体模块，再在多个模块重复证明之后抽成 common。这个偏好不是一开始写出来的，而是在持久化、缓存、安全、接口、存储、认证和 common 多轮波动中逐步留下来的。

## 演进趋势

Sandwich 的提交记录显示，项目逐渐从“能运行”，走向“可约束、可修复、可持续演进”。这条路不是靠一次完整设计铺出来的，而是通过高频小步提交、快速试错和快速回滚、文档与门禁反复配合完成的。可以看到，系统在每一次迁移后都继续清理旧口径，在每一次抽象后又检查它是否越界；到后期，common 地基变得更完整，业务语义也更少依赖全局常量、旧基类和模糊工具层。项目的形态因此从“把功能接起来”，慢慢变成“让每个边界都能解释自己为什么存在”。
