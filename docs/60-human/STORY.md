# Sandwich 项目故事

本文是 Sandwich 的演进叙事，不是实现规范。

* 不作为工程规则依据
* 不作为 AI 默认输入文档
* 不作为架构设计说明

只记录“这支团队（含 AI）如何判断、取舍、修正”。

文中所有判断，均基于 commit 行为的观察性推断，而非作者主观表达。

---

## 第一阶段：旧项目先被接管，而不是被重写

【触发点】

最早的提交从 `Initial commit`、`init` 开始，但很快出现 `Add docs governance entrypoints`、`Docs(governance): 搬运文档串联与提交策略`、`Chore(api): 切换入口模块为jar打包`、`Refactor(api): 清理服务端页面依赖`。这组提交不像从零搭一个理想项目，更像 AI 先接手一个已有项目，把入口形态、文档入口和协作方式固定住。

固定背景里，Sandwich 是 Bacon 的落地演示项目。从提交行为看，最早被搬进来的不是某个业务模块，而是 Bacon 的工程控制方式：治理入口、TODO 拆分、提交收口、持久化边界和 AI 读取规则。人类没有直接编辑文件，而是给出方向和判断；AI 负责把这些判断落成文档、目录和提交。

【关键动作】

第一批动作集中在三个方向：API 入口从旧页面口径切到 jar 运行形态；`docs` 和 `TODO` 被建立为协作入口；`sandwish-infra` 子工程被创建，字典、日志、菜单、机构、角色、上传文件、用户、存储、会员等持久化链路连续迁移到 infra。

这些提交颗粒度很小，常常是一个领域、一条持久化链路、一次 TODO 收窄。旧项目的混乱在这里表现为：入口形态不清、持久化职责混在业务中、Redis 状态归属不明、DO 和业务实体边界模糊。AI 没有一次性重写，而是先把混乱拆成可命名、可提交、可回退的小块。

【冲突 / 反复（关键加分项）】

这一阶段已经出现明显反复。`Docs(todo): 收窄认证 Redis 迁移子任务表述` 很快被 `Revert "Docs(todo): 收窄认证 Redis 迁移子任务表述"` 撤回，随后才是 `Feat(auth): 迁移认证 Redis 持久化到 infra` 和 `Feat(auth): 为 Redis 实体补充 DO 和装配器`。

这说明认证 Redis 的归属并不是一开始就稳定：它到底是缓存、运行态状态，还是持久化边界的一部分，需要在 TODO、回退、代码迁移、DO 装配器之间来回校准。这里的不稳定反而成为一种工作方式。AI 可以快速提交，也可以快速撤回；人类给出约束后，AI 再把判断落到文件结构和提交边界里。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎不是先追求完整新架构，而是先验证一个更务实的判断：旧项目要被 AI 持续控制，第一步不是重写功能，而是让混乱有地方登记、有边界可拆、有提交可收口。Bacon 的方法论在这里更像被搬进现场的一套施工规程，先保证 AI 每一步都能解释自己在改什么。

## 第二阶段：模型隔离让旧系统开始说分层语言

【触发点】

4 月 27 日出现明显密度突变，提交主题从“搬持久化”转向“模型怎么分层”。`Docs(governance): 固化接口模型分层规则` 之后，一组 `Feat(sys): 隔离用户接口模型`、`隔离角色接口模型`、`隔离机构接口模型`、`隔离菜单接口模型`、`隔离日志接口模型`、`隔离字典接口模型` 连续出现。旧项目里接口模型、领域实体、持久化对象混用的问题，在这一段被集中暴露。

【关键动作】

这一阶段先隔离后台系统、认证、辅助、前台会员登录状态等接口模型，再回到持久化表达，继续收敛机构、日志、字典、上传文件、存储、辅助、会员等 data object 和 assembler。与此同时，`Refactor(common): 收窄通用Crud契约`、`Refactor(sys): 收窄菜单树持久化契约`、`Refactor(common): 收敛实体查询契约`、`Refactor(api): 改用显式查询对象` 说明旧的万能 CRUD、树服务和查询基类也开始被怀疑。

旧项目的混乱在这里不再只是“代码放错目录”，而是不同层拿同一种对象讲话。接口层、业务层、持久化层如果共用模型，AI 后续很难判断一处改动会影响哪个边界。模型隔离因此不是美化，而是在给 AI 建立可推理的地图。

【冲突 / 反复（关键加分项）】

这一阶段的波动点是 common 的边界。提交一边收窄通用 Crud、树和查询契约，一边又拆分公共基础模块、引入 MyBatis-Plus 基础配置。看起来不是简单地“扩大 common”或“删除 common”，而是在验证什么可以成为公共能力，什么只是旧项目里遗留的便利封装。

这种反复通常意味着作者的思路正在从“复用已有工具”转向“只保留能被治理的公共契约”。旧项目里的 common 很可能曾经承载太多默认行为；搬运 Bacon 的规则后，AI 开始把这些默认行为拆开，只有稳定、可命名、可测试的部分才留下。

【思路历程推测（观察语气）】

从这些提交看，更像是在把旧项目翻译成 Bacon 能控制的语言：HTTP 入口有请求响应模型，持久化有 DO 和 assembler，业务查询有显式 query，公共模块不再默认代表业务便利。作者的思路似乎从“把功能迁出来”转向“让每一层都能被规则描述”。

## 第三阶段：文档不再只是说明，开始变成门禁

【触发点】

同在 4 月 27 日，commit 类型再次变化：`Docs(api): 明确Request注解规约口径` 后面紧跟 `Test(api): 增加Request注解规约门禁` 和 `Test(api): 迁移Request必需注解`；Response、DO 注解也出现同样的文档与测试组合。这里可以看到 Bacon 的文档规则被进一步搬运：规则不是写完就结束，而是要变成可运行的架构约束。

【关键动作】

关键动作包括建立 `common-test` 规约模块，增加 Request / Response / DO 注解检测，把 API 模型和持久化对象的注解要求变成测试。随后缓存边界、安全迁移也采用同样路径：先有判断手册、迁移手册、现状盘点，再有代码迁移、测试补齐和现场清理。

权限整改尤其典型。`Docs(security): 制定权限整改运行手册` 之后，连续出现通用权限匹配模块、权限会话服务、登录写入权限会话、Spring Security 令牌认证、权限会话认证测试。工程规则开始接管口头约定，旧项目中的安全行为不再靠散落代码理解，而是被重写成服务、过滤器、测试和文档闭环。

【冲突 / 反复（关键加分项）】

缓存是这一阶段最明显的不稳定事件。提交先有 `Docs(cache): 增加common-cache判断手册`、`Docs(cache): 盘点缓存迁移现状`、`Docs(cache): 固定infra缓存契约`，然后是 `Docs(cache): 确认暂不建立common-cache`。但很快又出现 `Docs(cache): 制定common-cache迁移计划`、`Feat(cache): 建立common-cache基线`、`Feat(cache): 接入应用JetCache配置`，并迁移系统、存储、认证、辅助状态到 JetCache。

这不是简单前后矛盾，而是一个判断逐步稳定的过程。缓存一开始更像 infra 内部实现细节；随着多个模块重复出现缓存状态、版本、运行态隔离需求，common-cache 才变成可被接受的公共能力。所谓搬运，在这里不是把 Bacon 的模块名照抄进来，而是把 Bacon 的判断方式放到 Sandwich 的旧问题里测试：先收窄，再观察重复，再抽象。

【思路历程推测（观察语气）】

这一变化通常意味着作者不满足于“AI 能改代码”，而是在让 AI 按固定节奏学习项目：先写判断，再做迁移，再用门禁固定，再清理现场。AI 高频小步提交让这种试错成本显著降低；人类不需要手工编辑文件，而是通过指令推动 AI 撤回、收紧、重做和固化。

## 第四阶段：技术底座替换暴露出更多旧口径

【触发点】

4 月 28 日，提交主题集中到 MyBatis Plus。`Docs(persistence): 制定 MyBatis Plus 迁移手册` 之后，签名、会员、存储、日志、菜单、机构、角色、上传、用户加密、用户、字典等持久化连续迁移。这是一次密集的技术底座替换。

【关键动作】

这一阶段先修 Mapper 扫描和 DAO 分页契约，保证新底座可以跑；随后删除旧分页和 CRUD 支撑，统一分页参数与 upsert 命名。紧接着，`Build(quality): 搬运 Bacon 格式化配置` 出现，之后按 common、biz、infra、admin、front 逐个应用格式化。

可以看到，Bacon 的搬运从文档规则延伸到了工程质量规则。格式化配置不是人类手工复制后放着不管，而是由 AI 搬入、执行、按模块消化。随后又删除 DO 手写访问器、无效 DO 主键构造器、DO 查询冗余字段，明确 DAO 写入语义，使用持久化主键生成，并固定 DO 主键生成规约。

【冲突 / 反复（关键加分项）】

这一阶段的反复不是大规模 revert，而是“迁移后继续拆脚手架”。MyBatis Plus 迁移完成后，项目没有停在能运行，而是马上清理旧分页、旧 CRUD、手写访问器、无效构造器和冗余字段。这说明技术底座替换只是显影剂：它让旧项目里那些为了跑通而留下的模糊结构暴露出来。

格式化配置也有类似意义。它表面上只是 style，但在 commit 序列里，它和 `validate执行spotless格式化`、成员声明顺序门禁、注解门禁一起出现，说明作者的思路似乎在从“代码内容正确”转向“代码形态也必须可治理”。对 AI 来说，形态稳定本身就是可持续控制的一部分。

【思路历程推测（观察语气）】

从这些提交看，作者似乎在验证另一个判断：旧项目不能只迁移功能，还必须迁移生成规则。AI 生成的代码如果没有统一格式、统一 DO 规则、统一主键策略，很快会再次滑回混乱。Bacon 的搬运因此逐渐从“规则文档搬运”变成“构建流程、测试门禁和代码形态一起搬运”。

## 第五阶段：领域重塑把语义从工具层里拿回来

【触发点】

4 月 29 日到 4 月 30 日，提交从持久化转向领域模型。`Refactor(common): 引入实体主键值对象`、`Docs(governance): 增加领域实体重塑手册`、`Test(architecture): 固定领域实体回流门禁` 后，系统、辅助、存储、会员实体被连续迁移。这说明项目开始处理更深的混乱：对象不只是存储记录，也应该承载业务语义。

【关键动作】

这一阶段先增加实体主键值对象、领域能力接口和架构门禁，再迁移用户角色、基础实体、树形实体、辅助实体、存储实体、会员认证实体。之后又删除旧实体继承链、归拢领域能力接口、删除无意义 ID 构造器、统一领域实体 ID 访问、删除领域身份基类，最终合并领域基类到实体。

领域枚举也成组出现：异步任务状态、存储归属类型、日志类型、用户角色标记、菜单显示标记、会员启用标记、存储标记被改为业务枚举或业务状态。旧项目中 `"0"` / `"1"`、`flag`、全局静态常量、薄方法和工具方法承载语义的情况，开始被类型和命名替代。

【冲突 / 反复（关键加分项）】

领域基类是这个阶段最有张力的波动点。提交先增加领域能力接口，又迁移实体；随后删除旧实体继承链、删除领域身份基类、提升 Lombok 访问器、展开默认值初始化、最终合并领域基类到实体。也就是说，项目一开始需要基类帮助 AI 组织迁移，但当迁移推进后，基类本身又变成间接性来源。

这一阶段很能体现“搬运”的真实形态：不是把一套领域模型模板从 Bacon 复制过来，而是先把旧项目实体拉进一个可治理框架，再根据实际摩擦删掉多余中间层。规则被搬来后要接受旧项目检验，不合适的部分也会被 AI 按人类约束撤掉。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎从“让实体符合领域化形式”转向“让实体直接表达业务语义”。这很微妙：一开始可能需要接口、基类和值对象来摆脱旧结构；后面则更看重具体实体、具体枚举和具体方法名。AI 在这里承担的是反复试错的执行，人类提供的是“这层是否真的有意义”的判断。

## 第六阶段：接口层和查询层被二次修剪

【触发点】

5 月 1 日到 5 月 2 日，提交再次回到接口层，但主题不再是初次隔离，而是拆掉隔离后留下的新壳。`Refactor(interface): 移除接口装配器Spring依赖`、`Refactor(interface): 展开接口装配基础映射`、`Refactor(api): 下沉HTTP接口契约到控制器`、`Refactor(api): 静态化接口装配器`、`Refactor(api): 删除接口装配器ID转换壳` 连续出现。

【关键动作】

这一阶段做了三类修剪。第一类是装配器去状态化：接口装配器不再依赖 Spring，ID 转换壳被删除。第二类是控制器 REST 化和显式化：控制器通用工具被展开、基类绑定被删除、模块路径状态被移除、分页响应工具被提取。第三类是服务查询对象迁移：字典、菜单、角色、用户、机构、日志、存储、会员、签名等查询对象迁到明确目录，并用架构测试禁止 setter。

旧项目的混乱在这里更细：第一轮模型隔离解决了实体外泄，却可能产生过度包装。AI 继续按小步提交把这些包装拆掉，让请求绑定、参数校验、响应转换回到入口附近，让业务查询语义进入 service query。

【冲突 / 反复（关键加分项）】

这里的波动点是“隔离之后的壳”。4 月 27 日先隔离接口模型，5 月 1 日又删除未使用 API 模型、无效查询参数、无效 VO、装配器 ID 转换、控制器基类。这个阶段不稳定的地方在于：为了摆脱旧项目混用模型，先产生了一批新结构；当这些结构被 AI 生成出来并通过项目检验后，又被继续收窄。

这说明 Sandwich 的治理不是追求更多层，而是追求可解释边界。搬运 Bacon 的分层规则之后，项目并没有把规则绝对化，而是继续根据实际提交反馈修正：有必要的边界保留，无意义的壳删除。

【思路历程推测（观察语气）】

作者的思路似乎在这一段变得更成熟：不是“越规范越好”，而是“规范必须减少混乱”。从提交看，AI 正在被训练成一个会清场的执行者：完成迁移后继续删除无引用模型、无效方法、死工具类和旧控制器形态，直到边界真正轻下来。

## 第七阶段：业务纵深开始验证治理是否真的能落地

【触发点】

5 月 3 日到 5 月 4 日，提交密度再次升高，但主题从通用治理转向 storage 和 auth 两条业务纵深。前台登录 REST 化、前台认证控制器合并、旧签名拦截和 UEditor 支撑删除之后，存储需求、数据库设计、上线检查清单、存储安全、分片上传、认证身份凭据、会话运行态、OAuth 迁移连续出现。

【关键动作】

存储侧先补私有资源访问校验、业务绑定查询过滤、资源逻辑删除、业务绑定约束，再引入本地存储后端抽象、分片上传持久化模型和分片上传业务编排。认证侧先固化需求和数据库设计，再增加后台登录标识、认证凭据、认证会话业务对象和持久化，切换后台登录身份凭据认证，写入会话生命周期，并补模型测试。

随后认证会话 Redis 运行态被单独拉出来：先下达任务并固定口径，再增加运行态端口、实现 Redis 存储、切换优先生命周期、补测试、清理 TODO 和失效 runbook。OAuth 也走出类似闭环：客户端、授权、刷新令牌、访问令牌、撤销状态、多登录方式、授权码流程、令牌正规化、测试和文档清理。

【冲突 / 反复（关键加分项）】

认证状态的归属是这一阶段的关键波动点。早期已经处理过 Redis 持久化归属，到这里又重新出现会话运行态 Redis 迁移。但这次不是重复，而是更细地拆分事实和运行态：认证会话作为业务对象持久化，Redis 作为运行态优先生命周期存储。旧项目里“登录状态到底是什么”的混乱，被拆成不同对象、端口和生命周期。

OAuth 中 `Refactor(auth): 移除认证租户口径` 也是一个收缩信号。系统没有为了完整性保留多租户语义，而是在当前项目不成立时撤掉它。这里可以看到人类判断对 AI 的约束：不是所有看起来高级的能力都该保留，治理的目标是可控，而不是堆满概念。

【思路历程推测（观察语气）】

从这些提交看，作者似乎在用 storage 和 auth 检验前面搬来的方法论是否有效。需求、数据库、领域对象、持久化、运行态、测试、清场可以围绕真实业务反复闭环，这说明 Bacon 的规则不只是文档管理技巧，而开始变成旧项目演进的执行系统。

## 第八阶段：common 地基被重新允许扩张

【触发点】

5 月 5 日，提交主题集中到 common 框架骨架和旧模型清理。前半段先清理系统域具体语义：用户身份凭据、用户认证字段、用户实体角色承载、部门薄方法、用户等级值对象、访问等级值对象、旧上传文件模型、旧验证码 Servlet。随后出现 `Feat(swagger): 增加通用Swagger配置模块` 和 common-web、common-core、common-security、common-mybatis、common-log、common-mq、common-oss 的连续提交。

【关键动作】

这一阶段补齐统一 API 响应、统一异常、异常响应处理、请求上下文传递、当前用户契约、统一 ID 生成、EntityId 类型处理器、JSON 列表类型处理器、统一响应包装 Advice、声明式权限注解、Spring 当前用户解析、后台接口权限注解、common 自动配置和架构规则复用支持。

随后又增加统一操作日志框架、统一消息发送门面、并发和路径架构规则、API 注解架构规则、对象存储抽象、本地和 S3 实现，并基于对象存储重建 storage 后端适配。旧本地存储后端、全局静态配置、无效异常构造方法和失效占位文件被清理。

【冲突 / 反复（关键加分项）】

common 在前面多次被收窄，删除 CrudService、RedisClient、无效公共类；到了这里又被大规模补齐。这不是反复横跳，而是抽象条件发生了变化。早期 common 里混着业务默认行为，必须收窄；后期多个模块已经重复证明了统一响应、上下文、权限、ID、消息、对象存储这些能力的稳定性，common 才重新扩张。

`Build(quality): 搬运 Bacon 格式化配置`、`Docs(prompts): 搬运项目故事提示词`、`Docs(agent): 收口人类文档加载规则` 这些提交也让 Bacon 背景更清楚：被搬运的不只是代码工具，而是 AI 协作中的规则、提示词、人类文档边界和故事生成方式。到这一阶段，搬运已经从“拿来一些文档”变成“让 Sandwich 自己拥有一套可运行的治理节奏”。

【思路历程推测（观察语气）】

作者的思路似乎在这里完成一次转向：不是排斥 common，而是要求 common 通过旧项目问题的反复验证。所谓搬运，在这里更像是把 Bacon 的工程判断放进 Sandwich 中跑一遍，只有那些被多个模块重复需要、能被测试固定、能减少混乱的规则，才变成 Sandwich 自己的地基。

## 第九阶段：从后端治理扩展到真实运行和前端入口

【触发点】

5 月 5 日后半段到 5 月 6 日，提交从代码治理走向部署、真实环境和 admin-web。数据库基线脚本、Docker 部署样例、API 配置清理、Redis 配置、对象存储环境变量、GitHub PR 质量门禁、真实环境冒烟脚本、本地 Swagger 启动链路、前后台启动入口命名连续出现。随后 `Feat(admin): 初始化后台前端工程` 和后台前端组件库、路由菜单、规约、登录页、权限菜单接入出现。

【关键动作】

这一阶段做了两件事。第一件是把系统从“测试能过”推进到“本地和部署能启动”：数据库基线、deploy、环境变量、Swagger、本地调试、真实环境冒烟脚本和 PR 门禁都被补齐。第二件是把治理扩展到前端：后台前端工程初始化、组件库、路由菜单、前端代码规约、登录页面、权限菜单、命名目录规则、全局类型归属、根路径别名、前端边界门禁逐步出现。

同时，后端继续收紧：响应包装迁移、验证码图片适配、Swagger 排序、当前用户接口契约、公开方法约束、查询对象序列化声明移除、服务接口方法重载禁止、用户账号服务拆分、当前用户菜单过滤、接口权限注解收敛。

【冲突 / 反复（关键加分项）】

这里的波动点是前后端治理的衔接。admin-web 不是单纯新增页面，而是先接入基础工程和规约，再接登录态、权限菜单、页面目录、服务归位和边界门禁。也就是说，前端一进入项目，就被放进了已经形成的治理框架里。

另一个反复是响应包装：先通过公共 Advice 建立统一响应，后面又有响应包装迁移手册、辅助签名响应包装、认证响应包装、移除响应包装过滤器、统一包装分页响应。这说明旧项目里响应口径并不统一，AI 需要多轮迁移、补丁和测试，才能让运行行为与治理规则一致。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎从“后端能被 AI 控制”扩展到“整个可运行产品都要被 AI 控制”。部署、冒烟、PR 门禁、前端目录、登录权限、响应包装都被纳入同一套节奏。人类没有直接编辑文件，而是在不断指定新的治理边界；AI 则把这些边界落实成工程、测试和提交。

## 第十阶段：全局 ID 和审计把治理推向更深的对象生命周期

【触发点】

5 月 7 日，提交密度再次爆发。先是 admin-web 字典、部门、前端规则和缓存载体修复，然后出现 `Docs(audit): 增加数据审计需求`、`Feat(audit): 增加审计数据库基线`，紧接着是一整组雪花 ID 迁移：治理规则、系统/认证/存储/会员/审计数据库设计、schema、初始化数据、部署说明、领域标识、主键生成器、MyBatis 类型处理、各 domain ID 类型、API 边界 ID 类型、最终收口。

【关键动作】

这一阶段先补系统枚举字典初始化，再进入审计需求和审计数据库基线；随后全局雪花 ID 被拆成文档、SQL、数据、代码、domain、infra、API 边界和最终收口。每一步都有明确提交边界：先固定规则，再改数据库设计，再改 schema 和初始化数据，再改 common ID 能力，再按 domain 迁移业务和持久化 ID，最后迁移 API 边界并收口 RUNBOOK。

审计部分虽然还没有完全实现运行时，但已经能看到方向：Audit 被定义为独立业务支撑模块，旧的 `Auditable`、`del_flag`、旧持久化审计字段、Service Command 化、`AuditMeta` / `AuditLog`、后台查询入口开始进入需求和 RUNBOOK。这个主题说明治理已经不只针对代码结构，而是开始管理业务对象生命周期和操作可追溯性。

【冲突 / 反复（关键加分项）】

雪花 ID 的迁移体现了很强的“搬运后再项目化”特征。它不是在某个文件里把 String 改成 Long，而是先讨论 ID 规则、审计 objectId 是否仍为 String、idempotencyKey 与 id 的区别、expectedVersion 如何产生，再拆成 RUNBOOK 和 TODO，最后按文档、SQL、代码、API 边界逐段提交。

这一阶段也有收缩：`Docs(audit): 收窄审计服务改造手册` 把已经完成的雪花 ID 从 Audit RUNBOOK 中删除，只保留审计服务改造本身。可以看到，RUNBOOK 不是试验田，而是执行手册；当全局 ID 独立完成后，它不能继续混在审计改造里。作者的思路似乎在进一步收紧：每套手册只承担一个目标，每个目标完成后就清场。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎已经从“把旧项目治理起来”转向“让治理本身可复制”。雪花 ID 迁移展示了一种成熟的搬运路径：先从方法论中搬来规则表达方式，再针对 Sandwich 的现实拆出独立 RUNBOOK，再用 TODO 控制文件级任务，再小步提交，每个提交都可验证，最后删除 RUNBOOK、收窄 TODO、保留 commit 作为完成历史。

## 第十一阶段：认证系统被重新拆开，主体语义开始统一

【触发点】

雪花 ID 和审计之后，提交焦点明显转向 auth。先是 `Refactor(auth): 迁移认证过滤器响应包装路径`、`Refactor(auth): 明确后台认证服务命名`、`Refactor(architecture): 约束入口认证服务归属`，随后前台会员认证被补齐：会员主体模型、会员标识和凭据模型、会员登录表单运行态、注册接口、会员认证会话和 token、前台 token 认证。这一组提交说明，认证已经不只是“后台登录能用”，而是开始跨 admin、front、OAuth 统一表达。

【关键动作】

这一阶段先把会员认证补成完整链路，再删除旧归属：`Refactor(member): 收口前台会员认证边界`、`Refactor(auth): 收口前台会员认证归属`、`Refactor(auth): 迁移权限会话与登录密钥服务归属`、`Refactor(auth): 删除独立登录密钥接口`。随后进入 Principal 改造：定义认证主体基础对象，增加统一认证主体结构，拆分统一认证主体服务，制定 Principal 迁移手册，再把认证读写迁到 Principal。

这里的旧项目混乱表现得很集中：后台用户、前台会员、OAuth 客户端、登录标识、凭据、会话、token 曾经各自有命名和生命周期。提交没有直接把它们揉成一个大对象，而是先统一主体结构，再删除后台旧身份凭据模型、会员旧身份凭据模型、旧 SQL 和旧测试。可以看到，AI 不是新增一套新模型就结束，而是继续把旧模型从代码和数据库口径里清掉。

【冲突 / 反复（关键加分项）】

这一阶段最明显的反复是“先补会员，再合 Principal”。如果只看单个提交，会觉得前台会员认证刚刚被完整建立，紧接着又被 Principal 改造吸收。但从连续行为看，这更像是在先让前台链路具备完整事实，再把后台/前台/OAuth 放进统一主体语义中。否则统一模型会缺少会员侧的真实压力测试。

这种节奏很像 AI 参与下的可持续试错机制：先补齐一条链路，让它有测试和边界；再发现重复语义；再把重复语义抽成 Principal；最后删除旧链路。成本被小步提交摊薄，人类可以在每个判断点收紧方向，而不需要手工重排所有文件。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎从“后台认证迁移”转向“认证主体治理”。`Principal` 不像一个新功能，更像一个被旧项目多条认证链路逼出来的语义中心。Bacon 的方法在这里继续发挥作用：先用 RUNBOOK 明确目标，再让 AI 小步迁移，再用测试和删除旧模型证明新语义真的接住了旧行为。

## 第十二阶段：PreAuthSession 把登录前状态从业务编排里剥离出来

【触发点】

Principal 收口后，提交进入 PreAuthSession：`Docs(auth): 制定PreAuthSession迁移手册`、`Feat(auth): 下沉后台PreAuthSession服务`、`Feat(auth): 下沉会员PreAuthSession服务`、`Refactor(auth): 统一入口预认证会话命名`、`Docs(auth): 同步预认证会话目标设计`。这组提交说明，登录前状态也开始被独立建模。

【关键动作】

PreAuthSession 的动作很集中：先把后台和会员入口的预认证会话服务下沉，再统一入口命名；随后 `Feat(auth): 增加预认证会话能力`、`Refactor(auth): 删除旧登录表单链路`、`Fix(auth): 收紧预认证会话过期判断`、`Test(auth): 精简预认证会话测试`、`Refactor(auth): 隔离预认证会话缓存模型`。从这些动作看，验证码、临时密钥、登录前 token 和 refresh token 不再散落在 Controller 或 AuthService 里，而被收束为一个短生命周期运行态。

PreAuthSession 后面又出现 `Fix(auth): 修正预认证会话DAO命名`，这是一个很小但有意义的补丁。它不是业务功能，而是架构门禁阻止了 DAO 命名漂移。说明到这一阶段，AI 的改动已经会被命名规则及时拦住，修复也能被小步提交收口。

【冲突 / 反复（关键加分项）】

这个阶段的不稳定来自“登录前状态到底是不是 token 体系”。提交最终没有把 PreAuthSession 拆成正式 AccessToken / RefreshToken，而是保留预认证会话自身的 token 和 refresh token 作为访问句柄。旧登录表单链路被删除，缓存模型被隔离，说明作者更像是在验证一个判断：登录前状态是临时会话，不应和登录后的 Principal token 体系混为一谈。

这里也能看到人类判断对 AI 的修正：从提交结果看，AI 并没有持续堆 service 方法，而是把生成规则、存储规则、TTL 判断和命名边界逐步收进 PreAuthSession。旧项目中“验证码生成”和“验证码存储”搅在一起的问题，被拆成能力和业务编排两个层次。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎在认证域里变得更细：不是所有短期凭证都叫 token，不是所有临时状态都归 AuthService。PreAuthSession 的出现，让登录前流程有了自己的生命周期，也让后续 Principal token 和 PrincipalAuthSession 的建模更容易保持干净。

## 第十三阶段：PrincipalAuthSession 让运行态会话成为统一承载点

【触发点】

PreAuthSession 之后，提交再次密集转向 token 和会话：`Refactor(auth): 合并主体令牌运行态`、`Refactor(auth): 清理旧后台访问令牌`、`Refactor(auth): 移除会话授权审计字段`、`Refactor(auth): 令牌状态改为枚举`、`Refactor(auth): 收敛认证会话与主体令牌表达`。随后出现 `Docs(auth): 制定主体认证会话改造手册` 和 `Feat(auth): 增加主体认证会话运行态`。这说明登录后的会话运行态被重新定义。

【关键动作】

这一阶段把后台、会员、OAuth 三条链路接入主体会话：`Refactor(auth): 令牌绑定主体认证会话`、`后台认证接入主体会话`、`会员认证接入主体会话`、`OAuth授权绑定主体坐标`、`OAuth令牌接入主体会话`。随后补 `PrincipalLoginEvent`：先增加主体登录事件模型，再写入主体登录事件。最后合并权限会话到主体会话，删除旧认证会话链路，补总验证，清理主体会话改造现场。

可以看到，PrincipalAccessToken / PrincipalRefreshToken / PrincipalAuthSession 的关系被重新整理：token 是客户端携带的外部表达，session 是运行态承载，PrincipalKey 是用户、会员等主体坐标，登录事件则负责落库留痕。权限不再单独有 PermissionSession，而是进入 PrincipalAuthSession 的 values，并且 values 不再有独立 TTL，而是跟随 session TTL。

【冲突 / 反复（关键加分项）】

这个阶段的关键波动点是“session 是否应该知道 token”。从提交结果看，最终更像是从 token 找 session，而不是 session 反向管理 token。旧的 AuthSession、MemberAuthSession、OAuthAuthorization、PermissionSession 都曾经带着各自的会话口径；后续提交把它们逐步压缩到 PrincipalAuthSession 和 PrincipalLoginEvent 两个方向：运行态在 Redis，登录历史在数据库。

最近的 `Refactor(auth): 收敛主体会话创建语义` 又把这个判断再推进了一层：`PrincipalAuthSession.create(...)` 只用于业务新建，`restore(...)` 用于 infra 还原；构造器被收成 private；规约测试禁止 infra 调 entity `create()`，也禁止业务侧调 entity `restore()`。这说明项目不只是靠约定理解“新建”和“还原”的区别，而是把这一区别固化成测试门禁。

【思路历程推测（观察语气）】

从这些提交看，作者的思路似乎从“统一 token”进一步转向“统一认证运行态”。这一步很容易失控，因为 token、refresh token、session、permission、OAuth authorization、login event 都有生命周期。但提交没有选择一个大而全的 AuthSession，而是让运行态、传输凭证、历史事件各自回到自己的位置。到这里，Bacon 的规则不再只是外部方法论，而像是已经内化成 Sandwich 的日常判断：业务创建归业务，持久化还原归 infra，语义一旦稳定就用架构测试守住。

## 演进趋势

Sandwich 的提交记录显示，它不是一个从零开始被设计得很干净的项目，而是一个旧项目被 AI 持续接管、拆解、修正和治理的过程。Bacon 提供的不是某个运行时代码依赖，而是一套外部工程判断：文档如何进入项目，TODO 如何拆分，RUNBOOK 如何执行，commit 如何收口，规则如何变成门禁。Sandwich 的意义在于，这些判断不是由人类手工搬运和手工维护，而是由 AI 在人类指令、约束和确认下持续执行。

可以看到，项目从一开始的持久化混乱、接口模型混用、公共层越界、Redis 状态不清、领域语义散落，逐步走向分层模型、DO/assembler、显式 query、架构门禁、统一 common 地基、真实部署、前端规约、全局 ID、审计设计和认证主体治理。这个过程不是一次性重写，而是先搬规则，再跑项目，再让旧项目的问题反过来修正规则。所谓搬运，在这里最终变成一种稳定偏好：把 Bacon 的工程控制方式放进一个真实旧系统里，由 AI 小步执行，用 commit 记录每次判断，用测试和门禁固化被保留下来的判断，用 RUNBOOK 和 TODO 管住还没有完成的判断。

到后期，Bacon 的规则不再只是被引用，而是变成 Sandwich 自己的提交、文档、门禁、部署和收口节奏。项目也因此从“能运行”走向“可约束、可治理、可持续演进”。更重要的是，它展示了一种 AI 工程化路径：人类不直接编辑代码和文档，而是持续给出方向和判断；AI 负责搬运、实现、验证、回退和提交；混乱在这个循环中被逐步识别，规则在这个循环中被逐步证明，项目也在这个循环中变成 AI 可以继续控制的对象。
